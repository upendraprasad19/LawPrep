# Law Prep coding and release checklist

Working standard from 27 October 2026. Applies to human contributors and every coding assistant. Read this with [discipline](discipline.md), the current task brief, [contracts](contracts.json), [threat model](threat-model.md), [security requirements](security-requirements.json) and [accessibility scope](accessibility.md).

Purpose: prevent common failures, catch regressions early and require evidence before release. This is not a promise of bug-free software or proof of production readiness. A checked box applies to a named change and tested environment, not to the product forever.

## Stack and boundaries

Current manifests define Node 24/npm 11, TypeScript, Next.js App Router for the public site/API, independent React/Vite/React Router learner, shared Zod contracts, Vitest, Playwright and ESLint. Use exact package/lockfile versions; this document does not authorize dependency upgrades. Supabase provides the Postgres/Auth/private Storage boundary. Its dedicated `lawprep-dev` project has the first owner-authorized catalogue schema and private bucket. Account/publishing services and UI are implemented; their confirmed database continuation is applied and SQL/public-HTTP tested. The owner completed actual email-link sign-in, verified enrolment and authenticated account/editor reads on 30 October. Custom code-email setup and broader authenticated provider acceptance remain pending. Future Capacitor packaging shares learner screens; native delivery remains separate work.

The earlier [C01–C22 coding baseline](../implementation/2026-10-23-coding-standards-proposal.md) and [industry research](../research/2026-10-23-engineering-standards.md) explain the decisions. This checklist is the daily entry point; its current-status section replaces historical implementation-status sentences in those proposals. Keep rules here, semantic ownership in contracts.json, executable gate configuration in quality-gates.json and per-change evidence in the ledger/review record.

## Use for every change

Copy [change evidence](change-evidence-template.md) into the existing task ledger or review note. For each applicable ID below record PASS, FAIL, BLOCKED or NOT_APPLICABLE, with evidence. Blank means unverified. PASS requires an observed result; NOT_APPLICABLE requires a scope reason. Missing infrastructure means BLOCKED, never PASS. Do not check this master document as if all future work were done.

1. **Before coding:** read the task and relevant checklist sections; describe expected student behavior, risk, affected writers/readers, data classification and the smallest useful verification. High-risk work needs independent plan review.
2. **While coding:** use focused modules and canonical services; write a meaningful failing behavior test first for features/bug fixes, implement, then observe it pass. Documentation, copy and reversible presentation-only edits need appropriate inspection rather than artificial tests.
3. **Before review:** inspect the whole change, run affected compiler/lint/boundary/tests, record commands/results and limitations. Include negative cases and real boundaries for permissions, persistence and concurrency.
4. **At a milestone:** run `npm run verify`, obtain independent current-source review, then run `npm run verify:milestone`. Material edits invalidate affected review; never rebind an old acceptance to a new fingerprint without actual review.
5. **Before a release:** satisfy software, content and operations evidence separately. Commits, pushes, hosted migrations, deployment, charges and native builds still require the owner's explicit instruction. Preparing files does not authorize applying them.

Copy/style changes are low risk; ordinary learner behavior is normal risk. Auth, ownership, schema, publication, scoring/timing, evidence meaning, subscriptions, AI context/quota and verification/release tooling are high risk. Normal product changes need independent code review; high-risk changes need independent plan and code/security/domain review. Final whole-product review remains required.

## A. Architecture, types and maintainability

- [ ] **A01 — Respect package boundaries.** Learner components use the typed HTTP client; database/provider/privileged operations belong in server modules. Auth SDK use is a documented browser exception. No Next server/Image runtime dependency in the standalone learner. Build and serve it independently. Evidence: import-boundary tests and standalone browser path. [S1,S2]
- [ ] **A02 — One contract across the boundary.** Inputs begin as unknown; parse request paths/query/body, provider data and HTTP responses with shared Zod schemas. Infer transport types; map database rows to explicit DTOs. Do not return entire rows or let clients choose protected fields such as role, owner or score. Evidence: malformed/oversized/extra privileged field cases. [S1,S3,S4]
- [ ] **A03 — Preserve strictness.** Keep TypeScript strict and Hooks linting enabled. No application any, unvalidated boundary casts, blanket lint disables or ignored type errors to finish a change. A narrow interoperability escape requires explanation and a behavior check. Evaluate indexed-access/optional-property compiler strengthening in its own reviewed change; those flags are not currently enabled. [S3,S5]
- [ ] **A04 — Keep rules readable.** Focus each module on one responsibility; use explicit names/units and small functions. Extract shared behavior when there is a real second consumer; avoid speculative frameworks. Domain scoring/scheduling/evidence functions receive data, clock and policy, with no browser/DB/provider/environment access. Evidence: deterministic domain tests and review. [Project baseline C12,C19]
- [ ] **A05 — Treat versions deliberately.** Pin new dependencies, update lockfile with the change, use npm ci for reproducible installation and review compatibility, release notes and vulnerability results. Do not use force/legacy-peer-deps or blind audit-fix upgrades. Review transitive production risk and record any justified exception with owner and revisit trigger. [S6]

## B. Writer–reader drift, state and failures

- [ ] **B01 — Name the authority.** For every changed critical concept populate contracts.json with writer, stored fields/units/null meaning, version, DTO/projection, every known consumer, invalidation rule and behavior tests. Dashboard, planner, revision, reports and AI share the same interpretation. A reference/path check cannot prove every consumer was found. [Project baseline C01–C03]
- [ ] **B02 — Trace both directions.** Search affected field/function names and meanings across packages, imports, migrations, caches and AI. Change writer and all readers together, or define an explicit supported compatibility window. Test action → persisted event/version → API → actual dependent projections with expected values. [Project baseline C02,C03,C21]
- [ ] **B03 — Keep meanings distinct.** Lesson completion is coverage; assisted/repeated/diagnostic answers are not fresh independent evidence. Understanding, retention and performance remain separate. Target changes remap relevance without deleting history. Test a helped answer across dashboard/planner/revision/AI as those consumers are introduced. [Project baseline C07]
- [ ] **B04 — Prevent stale account data.** Use full user identity plus relevant exam/cycle/version in cache identity. On logout/account switch cancel requests, clear private state and reject late responses from the prior session. On successful writes refresh all dependent projections. Evidence: A → logout → B with delayed A response, plus write/read refresh. [S5; project C08,C10]
- [ ] **B05 — Keep React state intentional.** Calculate derived values instead of duplicating them through Effects. Effects synchronize external systems, include dependencies and cleanup, and tolerate Strict Mode lifecycle checks. Mutations happen in deliberate event/service paths. Evidence: rerender/unmount/race tests where relevant. [S5]
- [ ] **B06 — Show truthful async states.** Distinguish loading, genuine empty, unavailable/error, permission denied, pending, saved and revision conflict. A failed DB call is not an empty catalogue or zero progress. Never display saved before durable acknowledgement, cache failure as success, or swallow a required write. Evidence: failure/recovery and conflict behavior. [Project baseline C09,C11,C20]
- [ ] **B07 — Bound effects and retries.** Use request timeouts/cancellation; retry only when semantics allow it, with bounded attempts/backoff. Reuse mutation identity across retries. Required work must finish durably or enter a tracked job/outbox; an unawaited promise after a server response is not delivery. [Project baseline C06,C18]

## C. API, identity and browser security

- [ ] **C01 — Authorize at the operation.** Verify the token/session server-side with the supported Supabase method; decoding or getSession alone is not proof of identity. Verify current role/ownership/access near data operations. Proxy redirects, hidden buttons and typed actor objects are not authorization. Never trust user-editable user_metadata for roles. Test anon, learner A, learner B, publisher and role revocation where applicable. [S1,S7]
- [ ] **C02 — Choose auth transport explicitly.** Current API client uses Authorization headers. Keep tokens out of URLs/logs. If cookies authorize a mutation, apply CSRF protection and appropriate cookie settings; CORS is not CSRF protection. Redirect/callback URLs and cross-origin allowlists must be exact and tested; no credentialed wildcard. Test expired/malformed credentials and safe return paths. [S1,S7,S8]
- [ ] **C03 — Validate and constrain every endpoint.** Explicit route/method policy, content type, bounded body/field/list sizes, pagination and server limits before expensive operations. Reject unsupported methods/input and prevent mass assignment. Rate-limit auth, imports, publication, AI and billing according to configured budgets. Request-local counters alone are not a multi-instance limit. [S8]
- [ ] **C04 — Minimize exposure.** Private/personal/assessment responses and auth refreshes use appropriate private/no-store behavior. Public caching must specify keys, version and invalidation; withdrawal cannot leave restricted data publicly readable. Check real response headers and framework caching, rather than assuming defaults. [S1,S7]
- [ ] **C05 — Protect secrets and rendering.** VITE_ and NEXT_PUBLIC_ values are public build output. Secret/service-role keys, DB passwords and AI/payment credentials stay server-side. Render reviewed structured content/plain text by default; any rich HTML needs maintained allowlist sanitization and safe link schemes. Private PDFs/keys never enter public assets. Evidence: malicious render/import tests, transitive import graph and emitted-asset scan. [S2,S7,S8]
- [ ] **C06 — Harden the deployed browser boundary.** Before release verify HTTPS, appropriate security headers/CSP, framing policy and referrer behavior on actual hosted responses; use HSTS only on the intended HTTPS deployment. Recheck callback/asset behavior with the chosen policy. Headers do not replace encoding, authorization or RLS. [S8,S9]
- [ ] **C07 — Keep security evidence scoped.** Expand the applicable ASVS 5.0.0 map as features arrive, with real requirement IDs, owning task, tests and actual result. Run relevant security/performance advisors after DB changes. A partial map or clean advisor output is not ASVS conformance or a full audit. [S9]

## D. Supabase, Postgres and migrations

- [ ] **D01 — Confirm environment first.** Confirm target ref/account, existing schema/migrations and test-data scope. Use dedicated synthetic development/test data; never reference-project or production credentials/data. Generate migration filenames with the current CLI, review SQL and record exact application target. No hosted writes under a read-only connection check. [S10]
- [ ] **D02 — Test RLS and grants separately.** Every exposed table has RLS and deliberate role grants. User-owned rows need ownership predicates, and UPDATE needs correct USING/WITH CHECK plus SELECT policy. Test real anon/A/B/publisher roles through intended DB/API paths, including direct Data API attempts and forged owner IDs. Superuser/service-role success cannot prove RLS. [S7,S11]
- [ ] **D03 — Restrict privileged surfaces.** Keep keys/editorial/roles private and grant least privilege. Prefer invoker views/functions. Any justified definer function needs narrow purpose, safe search_path/qualified names, explicit caller authorization and reviewed EXECUTE grants; put internal privileged helpers in a non-exposed schema. Definer functions are not a permission-error workaround. Audit views, RPCs and schema/default grants too. [S7]
- [ ] **D04 — Put invariants in Postgres.** Use foreign keys, NOT NULL/CHECK constraints and appropriate unique keys for identity, versions and mutation receipts. Related mutations, audit and required state changes share a transaction. Test actual simultaneous operations, including uniqueness/revision conflicts and bounded retry where needed. Sequential replay alone does not prove concurrent safety. [S12]
- [ ] **D05 — Reproduce the schema.** Replay migrations in an isolated resettable environment, check schema/policies/constraints and generate DB types from that result. Compare generated types with tracked output; do not hand-maintain a second DB model. Deployed migrations stay immutable; later changes use new migrations. Prove old/new application compatibility for staged releases. [S10,S11]
- [ ] **D06 — Bound database cost.** Use selected columns, bounded stable pagination and indexes supporting ownership/foreign-key/filter/order paths. Inspect realistic query plans when queries become material; measure before introducing extra services. Budget connections for the chosen deployment/pool mode; test transaction/driver compatibility and avoid a new pool per request. [S12]
- [ ] **D07 — Protect private objects.** Storage buckets and object policies enforce intended roles. Validate type/size and safe object names; signed links require authorization and short policy-defined expiry. Test direct download/upload/overwrite denial. Database backup alone does not back up Storage object bytes. [S7,S13]
- [ ] **D08 — Plan recovery before promotion.** Document additive rollout, data backfill validation, lock/downtime risks and repair/forward-fix path. Destructive actions need separately scoped approval and a verified backup. Run restore drills in isolation; record recovery time/data loss and separately restore private files. Free-tier access is not recovery evidence. [S10,S13]

## E. Law preparation correctness and editorial safety

- [ ] **E01 — Preserve provenance.** Every exam/cycle/eligibility/marking fact has an official source, checked date and version. Unknown future rules stay unknown. BLET means Patna; Panjab papers remain labelled analogues. Imports/AI drafts stay private/draft until source, rights, explanation, answer and mapping review. [Project design; Tasks 2,3,11]
- [ ] **E02 — Publish immutable versions.** Owner publication validates role, reviewed content, permitted sources/rights and complete required metadata. Publish/correct/withdraw actions are audited. Corrections create replacements and retain history; withdrawal removes future access without erasing completed-attempt references. Test the lifecycle through the actual catalogue reader. [Project design; Tasks 3,8]
- [ ] **E03 — Keep assessment authority server-side.** Snapshot question/key/marking versions; calculate score and deadline on the server. Refresh, retry, two tabs/devices, expiry and late save cannot extend time, duplicate a score or overwrite a newer answer silently. Use explicit UTC instants/units and injected clocks in domain tests. [Project design; Task 8]
- [ ] **E04 — Preserve earned history.** Subscription expiry/target switch/content correction does not silently rewrite scores or remove earned review. Any recalculation is explicit and separately labelled. Keep event time, received time and content/policy version distinguishable. [Project design; Tasks 5,8,9]
- [ ] **E05 — Explain learning evidence honestly.** Display evidence counts/dates and insufficient-evidence states; configurable heuristics are not scientifically validated readiness claims. Content volume and full-path coverage require per-exam editorial acceptance. Student reports enter owner triage and cannot directly edit keys/scores. [Project design; Tasks 9,11,11a]

## F. Optional AI and future billing

- [ ] **F01 — Keep AI constrained.** Server retrieves only approved sources and the caller's permitted evidence. Treat prompts/retrieved text as untrusted. Deny active-assessment help/key leakage. Validate structured replies, cited source IDs and known activity IDs; unsupported facts get an unsupported response. AI cannot directly write scores, roles, publications or billing. [S14; Tasks 13,14]
- [ ] **F02 — Keep AI optional and measurable.** Normal learning continues on outage/exhaustion. Atomic quota reservations, duplicate requests, timeout, crash/lease recovery and actual simultaneous last-unit requests are tested. Record provider/model/prompt/retrieval versions, latency/cost and separate real-provider evals from fakes. Critical privacy/assessment leaks block release even with a good average score. [S14; Tasks 13,14]
- [ ] **F03 — Require learner acceptance.** AI plan changes are previewable/editable proposals; acceptance verifies owner, authorized references and current revision. Generated examples remain labelled and outside official scoring/strong evidence. Persist help flags before relevant assistance. [Project design; Tasks 13,14]
- [ ] **F04 — Verify commercial events.** Once a provider is selected, verify raw-body signatures and server-owned customer/subscription binding before granting access. Test duplicate/out-of-order/concurrent events and expiry. Fixture adapters are disabled in production. Prices/terms/provider sandbox and live activation are distinct decisions; no working live payment claim from fixtures. [Project design; Task 12]

## G. Verification, accessibility and delivery

- [ ] **G01 — Test behavior at its boundary.** Vitest covers pure rules and service contracts; real HTTP tests cover transport; real Postgres/Supabase tests cover policies/constraints/transactions; Playwright covers student journeys on built assets. Use fakes for external failures and deterministic logic, not to certify DB permissions or real provider behavior. Each bug fix reproduces the symptom before repair. [S11,S15]
- [ ] **G02 — Keep tests trustworthy.** Synthetic isolated accounts/data, owned test lifecycle and cleanup; no production secrets. Assert user-visible values using accessible locators and retrying assertions; avoid arbitrary sleeps/shared state. Reset mocks; record traces/failures. Required tests must not pass with zero tests, skips, TODOs or hidden retries/flakes. Mutation proof is targeted at critical invariants and our gates, not a mandatory blanket platform. [S15]
- [ ] **G03 — Verify usable learning.** Keyboard/focus, meaningful headings/labels, status/error announcements, contrast, zoom/reflow, reduced motion and small-screen use. Check real sign-in, lesson, timed-test, saved-answer, review and report paths as built. WCAG 2.2 AA is the target; timing accommodations/exceptions need explicit evidence. Combine automation with manual keyboard/screen-reader checks. [S16]
- [ ] **G04 — Keep CI and dependencies safe.** Same gate registry locally/CI; required commands exist, really execute and fail closed. Pin Actions to reviewed full SHAs, least-privilege token permissions and no production secrets for untrusted PR code. Enable hosted required checks/branch rules only in the authorized GitHub stage and verify a deliberately failing change is blocked. [S17]
- [ ] **G05 — Observe and recover.** Structured request/operation IDs and redacted errors; no tokens, raw payment bodies or student conversations in routine logs. Before release demonstrate save failure detection, health/alert routing, dependency outage, cost limits and restore/repair. Define retention/deletion/export and responsible owner. Choose service targets from measured deployment behavior; no invented uptime promise. [S8,S13]
- [ ] **G06 — Give an evidence-based handoff.** Record scope/fingerprint, commands and outputs, reviewer findings/resolution, remaining blockers, browser/environment coverage and rollback/repair. Separate software, reviewed content and operations readiness. Do not label an entire app production-ready from the client milestone. [Project discipline]

## Exceptions and maintenance

Do not waive tenant isolation, secret protection, assessment authority, editorial publication checks or required real-boundary proof to meet a deadline. Resolve the issue or mark the feature/release blocked. Other exceptions record rule ID, reason, scope, risk, compensating control, accountable owner and expiry/revisit trigger. High-risk exceptions receive independent review; anything changing product scope/authorization returns to the owner. Never silently lower quality-gates.json requirements.

Revisit relevant guidance when changing a framework/SDK/provider, changing deployment/auth transport, or discovering an escaped bug. Update the owning rule/contract and a meaningful regression test together. Do not create another parallel checklist. Contributor/assistant entry points must link here; automation is evidence only for controls it actually checks.
