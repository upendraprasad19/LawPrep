## What writer-reader drift means for Law Prep

A writer saves a value; readers interpret it. Drift can involve a renamed field, a changed unit, a changed meaning, the wrong source, an outdated cache, or a different interpretation in an AI context. Shared TypeScript names alone cannot catch semantic drift.

Example: completing a lesson marks its topic covered. If the dashboard interprets that flag as mastery, the revision planner stops reviewing it and the AI says the learner understands it, all three readers are wrong even though the field exists and the code compiles. The same principle applies when total score is mistaken for accuracy, assisted answers for independent evidence, or minutes for seconds.

Trace the complete contract: student action -> authenticated API -> canonical mutation -> stored event/version -> canonical evidence projection -> dashboard, planner, revision, export and AI context. Browser/cache state is a projection, not another authority.

## Proposed enforceable rules

| ID | Rule | Evidence/enforcement and owning plan task |
| --- | --- | --- |
| C01 | One canonical mutation service per critical concept; canonical readers/projections own shared interpretations. Components call the typed API client; route handlers validate/authorize/delegate. Database calls stay in `packages/server`, with CLI/import code explicitly allowlisted where needed. Auth SDK calls are a documented client-side exception. | Import boundaries and known-bad fixtures in Task 1; service/API contracts in each feature task. Do not scatter direct table writes among screens, AI tools and webhooks. |
| C02 | Registry entries describe field meaning, unit, null behavior, ownership, storage/API mapping, writer, every known consumer, cache refresh and a behavioral contract test. New consumers of a registered concept must be listed. | Task 0 registry schema and fixture checks; Tasks 7–14 populate actual symbols/tests. A path checker proves references exist, not that the inventory is complete; review examines all consumers. |
| C03 | Rename or meaning/source change requires a cross-package consumer search and same-batch contract/test updates, including AI, imports, reports and cached selectors. Do not satisfy old readers with a silent, semantically wrong alias. | Task 0 diagnosis/review template; Task 9 fixtures prove coverage != understanding and assisted != independent. Backward-compatible parsing is added only for a real supported older version, with explicit normalization and retirement criteria. |
| C04 | Shared strict TypeScript/Zod contracts; external inputs start as unknown and are validated. No application `any`, unchecked casts at trust boundaries or duplicate handwritten API models. Schema-generated database types plus domain DTO adapters prevent database/API drift. | Task 1 typecheck/lint/invalid-input tests; Task 3 migration replay and generated-type diff. A comment does not make an unsafe cast safe. |
| C05 | Runtime authorization derives identity/role from verified server context. Use RLS-protected clients for ordinary user actions. Privileged operations need narrow capability/ownership checks, constrained inputs and audit evidence. | Tasks 3–5 real two-account RLS/API tests; Task 12 verified subscription binding. A typed actor object is documentation, not proof of authorization. Authenticated-only read access is insufficient for user-owned records. |
| C06 | Every mutation checks expected revision where concurrent edits matter and uses database uniqueness/transactions for idempotency. No read-then-write claim of exactly-once behavior without concurrent tests. | Tasks 7–8 and 12–14: duplicate submission, two-device answer conflict, webhook replay/out-of-order delivery, simultaneous AI requests and proposal acceptance. |
| C07 | Store immutable attempt/content/key versions and original evidence. Answer-key corrections never silently rescore old attempts. Scores/deadlines/access come from server code, not browser or model output. | Tasks 8–9 version-freeze, timeout and explicit-recalculation tests. AI uses the same deterministic score/evidence projections as the UI. |
| C08 | Cache identity contains full user ID and relevant exam/cycle/content version; logout/account switch cancels requests and clears user state. Late results from the old session cannot populate the new session. | Task 4 adds A -> logout -> B plus delayed-A-response browser tests; later features extend the same test to plans, attempts, entitlements and AI conversations. Never truncate IDs for cache namespaces. |
| C09 | An unavailable database is an error, not an empty course, zero progress, missing purchase or not-found response. Distinguish absence from failure in typed results and UI. Do not cache failure as successful empty data. | Task 3 catalog recovery test and Task 9 sparse-evidence vs unavailable-progress tests; site cache behavior tested at its actual framework boundary where used. No broad error-code shortcut when the code also represents unexpected multiple rows. |
| C10 | Every successful write refreshes all dependent projections. Public content writes invalidate relevant public caches; private responses remain private/no-store. Restricted/withdrawn content cannot be served by a stale public cache. | Task 3 publish/correct/withdraw -> catalog/guide reads; Tasks 7–10 answer/event -> plan/progress/revision refresh. Cache strategy differs for public guides and learner records. |
| C11 | Errors are handled or propagated with structured operation/request IDs and redacted diagnostic context. Do not swallow saves or display success before durable confirmation. Noncritical logging failure must not erase the primary result or expose credentials. | Tasks 7–8 pending/saved/failed states and retry/conflict tests; Tasks 12–14 webhook/provider failure tests. Task 16 synthetic telemetry check. No raw payment bodies, session tokens or student conversations in routine logs. |
| C12 | Use UTC instants for authoritative deadlines, explicit user timezone for study-day display and named units (`durationSeconds`, `minutesPerDay`, monetary minor units). Inject a clock in time-dependent rules/tests. | Tasks 6–10 timezone/midnight and unknown-date tests; deadlines survive refresh. Retries preserve original event time, not overwrite it with retry time. Keep created/occurred/received timestamps distinct when needed. |
| C13 | Configuration is validated and centralized. Keep provider secrets in server secret stores/environment configuration; nonsecret budgets/models/feature settings may use a versioned server-only configuration layer. No public credential fallback. | Tasks 1 and 13 missing-config tests, browser bundle scan and startup validation. Do not copy a generic settings-table requirement that would expose secret-bearing rows. |
| C14 | Migrations are CLI-generated, reviewed, replayed from a clean isolated DB, and accompanied by updated generated types, ownership policies and constraint tests. Validate intended schema, not just migration-file existence. | Task 3 and every later schema task; CI migration replay/type drift. Use compatibility rollout for data/schema changes. Avoid blanket IF NOT EXISTS clauses that conceal an incompatible existing definition. |
| C15 | Uploaded/imported/editorial/AI content is untrusted. Validate structure and size, sanitize safe rendering and preserve provenance/rights/review status. Paid assets and keys are never in public static folders. | Tasks 2–3 malicious import/render/private-storage tests; Task 11 publication gate. Do not assume a PDF extension proves its type/rights or an imported boolean proves correctness. |
| C16 | Server validates raw signed webhook bodies before effects. Bind events to server-owned merchant/customer/subscription records. Replays and out-of-order delivery are safe. | Task 12 sandbox fixtures and transaction tests. Developer fixture adapters remain isolated and disabled in production. |
| C17 | AI is a server-side optional consumer of approved facts and authorized student evidence; output is parsed/validated, including citations and plan proposal references. Prompts are not authorization. | Tasks 13–14 authorization/quota/source/prompt-injection/acceptance tests. Generated/unreviewed material cannot affect official scored mocks or strong understanding labels. |
| C18 | No untracked fire-and-forget for effects needed to fulfill a student request. A saved answer must be durable before confirmation; use a tracked task/outbox if a required effect must outlive a server request. | Tasks 8, 12–13 failure/retry tests; persistence/worker design only when needed. Avoid assuming serverless promises survive response completion. |
| C19 | Pure domain functions own scoring, evidence, scheduling and revision. They receive explicit data/clock/config; no database, browser, provider or environment access inside these rules. | Tasks 7–10 deterministic tests and import boundaries. Keep modules focused; avoid speculative abstractions and duplicate calculators. |
| C20 | Every learner async screen has loading, genuine-empty, error/retry and permission states; forms/tests also show pending/saved/conflict states as applicable. Reusable tokens/components maintain accessibility and responsive behavior. | Feature browser tests plus Task 15 keyboard, narrow layout and reduced-motion checks. Learning components must build independently of Next server features. |
| C21 | Regression tests assert actual values and meaning across write/read boundaries; grep tests only prove source shape/presence. Critical protections get deliberate mutation proof and representative browser/real-DB tests. | Each owning task; Task 0 ensures checks run and do not pass on zero tests. No full-suite rerun per keystroke; targeted iteration followed by applicable integration/release gates. |
| C22 | Lists/imports use bounded queries and stable pagination; critical foreign-key/ownership/due-time queries are indexed and reviewed with realistic data. Apply server request/rate/concurrency budgets before external calls. | Tasks 2–3 and 8/10/13 performance/large-input fixtures; inspect query plans for actual bottlenecks. Do not introduce Redis or another service without a demonstrated requirement. |

## Concrete drift proof to add during implementation

Use synthetic records, not claims about an official exam:

1. A student completes one lesson and answers a question with help. Database stores coverage plus assisted evidence.
2. Dashboard reports covered, with insufficient independent evidence; plan can still recommend practice; revision schedules a later check; AI context conveys those same separate facts.
3. Replaying the event changes none of these counts. Reopening on another device reads the same state.
4. Changing target exams preserves history but changes the mapping of relevant topics.
5. Updating the content/key version leaves an old completed attempt's score reproducible.
6. Signing out A and signing in B shows none of A's state, even if A's outstanding HTTP response completes after the switch.

Tests compare expected values across the relevant persisted/API/projection boundaries, not just the existence of a helper name. Corrupting assisted/fresh classification or replacing insufficient evidence with mastery must make the test fail.

## Reference rules deliberately adapted

- Ecosystem server-components/default Next Image rules apply only where appropriate in the Next.js public site. The learner is a standalone React/Vite bundle, so its screens must not import Next server rendering or image-runtime dependencies.
- AVYA Hive-first/offline sync, Riverpod invalidation and APK rules become online-first server authority, authenticated client cache lifecycle and browser/HTTP concurrency tests here. No offline replication engine is being added.
- AVYA's IST-first date-key convention becomes UTC storage plus explicit learner timezone display under Law Prep's accepted design. Never blindly shift timestamps twice.
- Ecosystem's secret-in-settings-table convention is not carried over. Prefer server secret stores and least-privilege nonsecret configuration.
- Ecosystem's manually maintained database types become generated schema types plus explicit domain adapters and clean migration replay. Use the current CLI's timestamped migration generation; do not copy contradictory historical naming instructions.
- Broad authenticated-read policy examples do not provide ownership isolation. Law Prep tests actual user A/B access and checks update USING/WITH CHECK predicates and grants.
- Current report-only architecture scanners and legacy drift baselines in a reference repository are not proof that violations are blocked. New Law Prep boundary rules get real CI wiring and known-bad fixtures, with no inherited debt allowance.
- Do not copy the assumption that a mandatory actor type makes a privileged call safe or a helper's sequential replay behavior proves concurrent idempotency. Verify runtime authorization and database transactions explicitly.

## Integration into the implementation plan

Task 0 establishes this small root rule/index/registry structure and gate wiring. Task 1 adds strict types/import boundaries; Tasks 2–5 add catalog/auth/data protections; Tasks 6–10 prove semantic progress/assessment/cache contracts; Tasks 11–14 enforce publication/access/AI rules; Tasks 15–16 verify the product and operations. Use risk-based review from the discipline proposal. Do not create every bespoke scanner up front: standard tooling, real behavioral tests and focused review come first; add a custom scanner only for a clear recurring class it can reliably detect.

Owner's current budget direction is free-tier-first. These engineering standards remain the same regardless of whether hosting is free or paid. Real operational guarantees must still match the selected provider plan and tested deployment.
